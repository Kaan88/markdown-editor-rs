# Spike: incremental syntect (highlight)

Throwaway code, kept for reference. Not committed, not pushed. Windows 11, release build (opt-level 3), single thread,
syntect `=5.3.0`, `default-features = false`, features `["default-fancy"]` (fancy-regex, the viewer's set-up),
`SyntaxSet::load_defaults_newlines()` and the `base16-ocean.dark` theme, as in `mv/crates/render/src/highlight.rs`.

**The machine was loaded the whole time** (28 logical cores, other agents building other spikes and the viewer, and
in two waves up to a dozen of my own bench processes at once). Every timing is a median with its range; read the
ranges. Where a quieter re-run exists it is the one in the tables and is marked "(q)". Raw outputs are in `raw/`.

## How it was measured

- Test data is generated by code (`src/lib.rs`), deterministic, nothing committed: a 50,000-line Rust file (1,605 KiB,
  longest line 95 bytes: fns, structs, doc and line comments, balanced `/* */` blocks, strings, raw strings, macros)
  and a 50,000-line Markdown file (2,989 KiB, longest line 592 bytes: headings, one-line paragraphs with
  bold/italic/code/links, lists, quotes, tables, fenced blocks of rust, json, python, bash, js).
- One "line" of work = `ParseState::parse_line` plus walking `HighlightIterator` over the ops (what a renderer must do
  to get coloured runs). State = `ParseState` + `HighlightState`. Time: `Instant`. Memory: a counting global allocator
  (exact live heap bytes, `bin/mem.rs`) and `K32GetProcessMemoryInfo` private bytes (too noisy to tabulate; in raw).
- Checkpoint spacing K: the state at the start of every K-th line is stored (K=1 is a state per line).
- Re-highlight after an edit: replace line N, restart from the checkpoint at or before N, run lines, and after each
  checkpoint boundary past N compare the new state to the stored one with `==`; stop when equal (converged) or at EOF.
- Each measurement is 5 to 7 repetitions (the "typical" rows are 40 different edit sites, once each; `REPS` env).
- Commands: `cargo build --release`, then `target/release/bench.exe load|full|edit|viewport|slice|eq|long`
  (env `FILE=rust|markdown`, `SCEN=n`, `REPS=n`) and `target/release/mem.exe`. `probe.exe` is the one-off that found
  which Markdown lines are slow.

## 1. Loading

Six separate processes, in ms (median, range). Machine loaded.

| | median | range |
|---|---|---|
| `SyntaxSet::load_defaults_newlines()` (the viewer's call; it is the bundled binary dump, 75 syntaxes) | 0.88 | 0.53-1.43 |
| `ThemeSet::load_defaults()` | 0.69 | 0.49-2.16 |
| re-dumped uncompressed set, `from_uncompressed_data` (359 KiB) | 0.49 | 0.34-0.80 |
| first 1,000 lines of the Rust file in a fresh process | 134 | 107-217 |
| the same 1,000 lines again | 93 | 65-159 |
| first 1,000 lines of the Markdown file | 871 | 580-1163 |
| the same 1,000 Markdown lines again | 687 | 570-1043 |

Loading is not a cost: the set is lazy, so the price is paid on the first line of each syntax (regex compilation),
about 40 ms for Rust by the difference above; a single cold first-line parse measured 16 ms (Rust) and 48 ms
(Markdown) in one run. The uncompressed re-dump is no meaningful win (0.4 ms) and I did not check it highlights
identically; the viewer does not do it. Do the first parse of a syntax off the UI thread or at file open.

## 2. Full-file highlight, and checkpoint overhead

7 runs (Rust, first quieter run shown) and 5 runs (Markdown). Median ms, range.

| | Rust 50k lines | Markdown 50k lines |
|---|---|---|
| parse only, no styling | 3,640 (3,264-4,283) | 25,059 (24,631-34,326) |
| parse + style, no checkpoints | 3,001 (2,888-3,124) = 16,700 lines/s, 0.5 MB/s | 24,826 (23,972-32,408) = 2,010 lines/s, 0.12 MB/s |
| + checkpoint every 1 | 3,041 (2,962-4,264) | 25,441 (24,484-34,302) |
| + checkpoint every 16 | 3,842 (2,982-4,194) | 27,881 (23,979-32,707) |
| + checkpoint every 64 | 2,895 (2,864-2,932) | 24,544 (23,854-31,286) |
| + checkpoint every 256 | 2,919 (2,877-3,428) | 23,931 (23,902-28,174) |

Cloning the states costs nothing measurable (125-205 ns each, below). Rust earlier run under heavier load: 4.0-4.9 s
for the same rows. The Markdown syntax in this set is about 8 times slower than Rust. Parsing without styling was not
faster than parsing with it (the styling walk is small; the first row ran first and absorbed warm-up noise).

Slowness of Markdown is in paragraph lines. In a 20,000-line probe, 936 lines took over 1 ms each and were 84% of the
time; the worst were 250-410 character one-line paragraphs with several inline `**bold**`, `` `code` ``, `[link](url)`
spans, at 30-50 ms each. Cost by line length (non-table lines): under 120 chars about 72-97 us mean; 120-200 chars 0.4 ms
mean (p95 1.3 ms); 200-300 chars 2.3 ms mean (p95 13.6 ms, max 50 ms); 300-700 chars 5.6 ms mean (p95 17 ms).
Tables 21 us mean, headings 25 us, lists 94 us.

## 3. Memory of stored state (50,000 lines)

Exact live heap from a counting allocator, one run each (allocation sizes are deterministic).

| storage | K=1 (per line) | K=16 | K=64 | K=256 |
|---|---|---|---|---|
| **Rust**: ParseState + HighlightState | 53.4 MiB (1,121 B/entry) | 2.74 MiB | 0.69 MiB | 0.17 MiB |
| Rust: ParseState + ScopeStack | 29.6 MiB (621 B) | 1.86 MiB | 0.47 MiB | 0.12 MiB |
| Rust: ParseState only | 24.3 MiB (509 B) | 1.53 MiB | 0.38 MiB | 0.10 MiB |
| **Markdown**: ParseState + HighlightState | 55.4 MiB (1,162 B/entry) | 2.31 MiB | 0.58 MiB | 0.15 MiB |
| Markdown: ParseState + ScopeStack | 25.1 MiB (527 B) | 1.56 MiB | 0.39 MiB | 0.10 MiB |
| Markdown: ParseState only | 20.2 MiB (424 B) | 1.26 MiB | 0.31 MiB | 0.08 MiB |

`size_of`: ParseState 56 B, HighlightState 96 B, ScopeStack 48 B; the rest is heap (the context stack and captured
strings). One state is 0.5-1.1 KB, so a state per line costs about 1 KB per line (about 1 GB at a million lines,
extrapolated, not measured). `HighlightState::new(&highlighter, path.clone())` rebuilt from the stored `ScopeStack`
was equal (`==`) to the original in 10,000 of 10,000 sampled states in both files (about 0.4-0.8 us), so
ParseState + ScopeStack is enough to store. Memory of the syntax set and theme themselves was not isolated.

## 4. State comparison

`ParseState` and `HighlightState` both derive `PartialEq`; it is cheap. Measured over every 5th line state (10,000
per file), ns, p50 / p99 / max:

| | Rust | Markdown |
|---|---|---|
| ParseState + HighlightState `==`, equal | 35 / 50 / 1,365 | 15 / 45 / 4,065 |
| ParseState `==` alone | 10 / 20 / 155 | 5 / 20 / 55 |
| HighlightState `==` alone | 25 / 35 / 110 | 10 / 25 / 105 |
| `==` against the next line's (different) state | 5 / 50 / 120 | 15 / 45 / 85 |
| clone of the pair | 205 / 235 / 2,320 | 125 / 305 / 1,055 |

Comparing at every checkpoint boundary is free next to the 50-500 us a line costs. No hashing needed.

## 5. Re-highlight after an edit

Lines processed and time, from the checkpoint before the edit until the state at a boundary matches (or EOF). One edit
replaces one line; the line count does not change. Timing medians over 40 sites (typical) or 5 runs (single site).

### Rust

| edit | K | lines until match | time ms median (range) | converged |
|---|---|---|---|---|
| typical: `let ` becomes `let _x` in a function body, 40 sites (q) | 1 | 1 | 0.16 (0.06-0.19) | 40/40 |
| | 16 | 16 | 1.48 (0.57-2.49) | 40/40 |
| | 64 | 64 | 5.87 (4.0-7.1) | 40/40 |
| | 256 | 256 | 23.3 (16.1-25.5) | 40/40 |
| type `/*` at line 10 | 1 / 16 / 64 / 256 | 49,990 / 50,000 / 50,000 / 50,000 | 87.7 / 84.4 / 87.5 / 84.9 (range 82-90) | 0/5 |
| type `/*` at line 25,000 | 1 / 16 / 64 / 256 | 25,000-25,168 (to EOF) | 44 / 43 / 49 / 58 | 0/5 |
| type `r#"` at line 10 | 1 / 16 / 64 / 256 | 11 / 32 / 64 / 256 | 0.14 / 1.9 / 4.5 / 21.3 | 5/5 |
| type `r##"` at line 10 | 1 / 16 / 64 / 256 | 49,990 / 50,000 / 50,000 / 50,000 | 157 / 168 / 199 / 241 (range 146-231) | 0/5 |
| type unbalanced `{` at line 25,000 | 1 / 16 / 64 / 256 | 25,000-25,168 (to EOF) | 2,303 / 2,207 / 2,245 / 2,237 (range 2,070-2,317) | 0/5 |
| type one `"` at line 25,000 | 1 / 16 / 64 / 256 | 25,000-25,168 (to EOF) | 440 / 435 / 441 / 455 (range 431-460) | 0/5 |

Reading these:
- A typical edit that changes no state converges at the first checkpoint boundary, so it re-runs exactly K lines
  (the block holding the edit); with a state per line it is the one edited line. Cost is K times about 60-95 us.
- `r#"` converged only because my generated file has a `"#` ten lines later; it is a real result of this data, not a
  property of raw strings. `r##"` has no closing `"##` in the file and runs to EOF.
- Anything that leaves a context open or one level deeper (`/*`, an unterminated `"`, an unbalanced `{`, which
  pushes a block context) never converges: everything below the edit is re-run. The cost then is the cost of the rest
  of the file in that state: 44-240 ms when the tail becomes a comment or raw string (the parser is cheap inside
  them), 0.44 s in an open string, and 2.3 s for 25,000 lines of normal code (about 90 us a line) under an
  unbalanced brace, so 4-5 s if it were at line 10. This is the normal case while typing `{` before the closing `}`
  exists, so plan for it: it is not an exotic worst case.
- The block comment at line 10 diverges to EOF here because the Rust syntax nests block comments and the file's later
  `/* */` blocks are balanced (the depth stays at 1).

### Markdown

| edit | K | lines until match | time ms median (range) | converged |
|---|---|---|---|---|
| typical: insert `x` in a text line, 40 sites (q) | 1 | 1 | 0.13 (0.03-16.8) | 40/40 |
| | 16 | 16 | 1.9 (0.5-38) | 40/40 |
| | 64 | 64 | 34 (4.9-91) | 40/40 |
| | 256 | 256 | 130 (38-207) | 40/40 |
| type a fence ```` ``` ```` at line 10 | 1 / 16 / 64 / 256 | 56 / 80 / 128 / 256 | 10.4 / 37.8 / 53.7 / 130 (ranges 8.9-141) | 5/5 |
| type a fence at line 25,000 | 1 / 16 / 64 / 256 | 68 / 80 / 128 / 256 | 10.6 / 15.4 / 68.3 / 255 (ranges 8.1-270) | 5/5 |
| type `<!--` at line 10 | 1 / 16 / 64 / 256 | 49,990-50,000 | 29 / 37 / 48 / 50 (range 20-53) | 0/5 |

The fence converged because it is closed by the next original closing fence (the file's fences carry a language tag, so
an opening one cannot close mine). A file whose fences have no info string would behave like `/*` and run to EOF.
Markdown edit times have a heavy tail from the slow paragraph lines (section 2); these rows ran partly with ten of my
own processes alongside, so the K=1 range top (16.8 ms) and the K=64/256 medians are inflated; the lines column is exact.

## 6. Highlighting only a 60-line viewport

From the nearest checkpoint at or before the viewport top, 200 random positions. Rust (q), ms:

| K | avg lines run | p50 | p95 | max |
|---|---|---|---|---|
| 1 (exact state) | 60 | 3.43 | 3.98 | 4.33 |
| 16 | 67.8 | 3.85 | 4.65 | 5.23 |
| 64 | 91.1 | 5.11 | 7.11 | 8.54 |
| 256 | 183 | 10.6 | 17.3 | 19.0 |

The same Rust test under heavy load was 5.3 / 4.3 / 6.1 / 15.6 ms p50 (max 7.4-30.6). Markdown (loaded): exact
state 26 ms p50, 57 ms p95, 106 ms max; K=16 43 ms p50, 109 p95, 182 max; K=64 39 / 91 / 153; K=256 85 / 175 / 249.
60 visible lines of Rust is 3.4-5.3 ms (3.4 ms/60 = 57 us a line) and of Markdown tens of milliseconds, so a
whole-viewport highlight does not fit in an 8 ms keystroke budget with room for layout and paint, and for Markdown
it does not fit at all.

## 7. Slices between events

Whole file in fixed-size slices, 3 passes pooled. Rust (q), ms:

| lines per slice | p50 | p99 | max |
|---|---|---|---|
| 25 | 1.46 | 2.02 | 2.83 |
| 50 | 2.88 | 3.74 | 4.93 |
| 100 | 5.74 | 7.15 | 10.9 |
| 200 | 11.4 | 13.4 | 16.1 |
| 400 | 22.8 | 25.8 | 28.9 |

Time-boxed slices (read the clock after every line, stop when the budget is spent), Rust (q): budget 1 ms gives slices
of p50 1.03 ms, max 1.24 ms, 18 lines at p50 (min 4); budget 2 ms gives p50 2.04 ms, max 2.17 ms, 35 lines at p50
(min 14). Per-line cost, Rust (q): mean 57 us, p50 45, p99 148, max 370 us.

Markdown cannot be sliced to 2 ms by line count: 25-line slices were p50 9.2 ms, p99 66 ms, max 128 ms (loaded). Even
time-boxed to 2 ms the max slice was 32 ms, because one line can cost that (per-line us: mean 481, p50 71, p99 14,642,
max 25,248). Only a cap on line length, or a different Markdown highlighter, changes that.

## 8. Cost of long lines

One kind of line repeated (about 400 KB per repetition, 7 repetitions, fresh state, quieter re-run), us per line
median (range), and the worst single line:

| line kind (syntax) | 200 chars | 2,000 chars | 20,000 chars |
|---|---|---|---|
| Rust statements (rs) | 395 (378-588), worst 0.78 ms | 3,756 (3,245-4,074), worst 6.0 ms | 42,954 (41,465-46,197), worst 55 ms |
| string with no closing quote (rs) | 994 (917-1,114) | 46,323 (45,128-48,776), worst 103 ms | 44,135 (43,994-61,584), worst 69 ms |
| JSON objects (json) | 148 (145-238) | 770 (630-972) | 6,461 (6,389-6,616), worst 6.8 ms |
| minified JS (js) | 562 (556-568), worst 1.0 ms | 3,964 (3,947-4,030), worst 6.1 ms | 49,486 (49,254-49,752), worst 52 ms |
| Markdown inline markup (md) | 162 (160-162), worst 13.7 ms | 1,536 (1,532-1,540), worst 17 ms | 15,267 (15,197-15,377), worst 29 ms |

That is about 2 us per char for Rust and JS (consistent with 57 us for the 32-char average line in section 7), 0.3-0.7 us
per char for JSON, 0.8 us for Markdown prose of this shape. Roughly linear, with two exceptions: the string with no
closing quote (my generator truncated off the closing quote, so every line after the first is inside the string) costs
23 us a char at 1,000-5,000 chars and about 50-100 ms a line, a plateau that looks like fancy-regex hitting its
backtrack limit, which I did not verify. If it is, note what syntect does with it (src/parsing/regex.rs, fancy
`search`): an error such as the backtrack limit is treated as "no match", so a pathological line is silently
highlighted wrongly and costs tens of ms instead of failing. And the Markdown rows above hide the 30-50 ms lines
that real one-line paragraphs with mixed inline markup produce (section 2); they depend on the mix of markup, not the
length alone.

## Conclusions and recommendations

1. **The synchronous part after a keystroke is the edited line only** (Rust 0.06-0.19 ms with exact start state), then
   further visible lines only while the end-of-line state still differs from the stored one, all inside a 1-2 ms
   time-box. A whole 60-line viewport is 3.4-5.3 ms for Rust and tens of ms for Markdown: it must not be synchronous.
   Everything else goes in time-boxed slices between events.
2. **Checkpoint spacing: 16.** It costs 2.7 MiB per 50,000 lines (about 55 B per line), a typical edit re-runs 16 lines
   (1.5 ms, background), and a viewport restart from the nearest checkpoint is 3.9 ms against 3.4 ms with exact states.
   64 is acceptable (0.7 MiB, 5.9 ms re-run, 5.1 ms viewport); 256 is not (23 ms re-run, 10.6 ms viewport). For huge
   files scale K so that the checkpoint memory stays under about 4 MiB (K = max(16, lines / 3,000), an extrapolation
   from 1 KB a state, not measured). Add a small cache of exact per-line states for the visible lines and a few around
   them (about 100 states, 100 KB) so the edited line can be re-run alone and compared exactly; I did not measure this
   combination, only its parts.
3. **Store ParseState + ScopeStack, not HighlightState** (32% less: 621 B against 921 B per entry at K=16 in Rust; rebuilt
   HighlightState matched 10,000 of 10,000). Compare with plain `==` on ParseState and the rebuilt HighlightState, or
   on ParseState alone if the scope stack is unneeded for the decision (not tested whether ParseState equality
   alone can differ from the pair; the pair is 10-35 ns, so just compare both). `==` is cheap (5-35 ns equal, worst
   1.4-4 us); no hashing.
4. **Expect never-converging edits to be routine**: typing `{`, `"`, `/*` or a fence before its partner exists re-runs
   the rest of the file (0.04-2.3 s of background CPU on 25,000-50,000 Rust lines, more if the tail is code). Mark
   checkpoints below the edit dirty, keep painting the old colours for lines not yet re-run, and re-run top to bottom in
   slices, the visible lines first once the checkpoint above them is valid; restart the job from the edit if another edit
   arrives. If the viewport is below the re-run front, paint plain or stale rather than parse from a far checkpoint
   synchronously.
5. **Slice size**: do not fix it in lines, time-box it. Read `Instant::now()` after each line and stop at about 1.5 ms
   (overshoot was at most one line: Rust max 1.24 ms on a 1 ms budget, 2.17 ms on 2 ms). If a fixed count is wanted
   for Rust code, **25 lines** (p50 1.46 ms, p99 2.0 ms, max 2.8 ms in the quieter run; 35 lines p50 for a 2 ms box). It
   must be re-derived per syntax: Markdown has no safe count.
6. **Limits (proposals from these numbers, not tested beyond the data above)**:
   - Line length: leave a line plain (do not parse it; keep the state unchanged) above **1,000 characters** for code
     syntaxes: at 2 us a char a 1,000-char line is about 2 ms, and the no-closing-quote case already costs 26-50 ms
     from 1,000 chars. For Markdown the limit has to be lower, about **200 characters**, since lines over 200 chars
     average 2-6 ms with p95 14-17 ms and a worst of 50 ms in this file. (Plain wrap-heavy prose paragraphs are the
     normal Markdown, so this will switch off highlighting on many real paragraphs; the alternative is a small
     hand-written Markdown line scanner, like the viewer's TOML one, instead of syntect's.)
   - File size: the whole Rust file (1.6 MB, 50,000 lines) takes about 3-5 s of background CPU, so reaching the bottom of
     a file takes roughly 2 s per MB of code. Highlight code files to about **2 MB / 100,000 lines** (about 4 s, a
     bit more with more lines); over that, plain. Markdown through syntect: about **300 KB** (about 8 s at 0.12 MB/s) or
     stay plain; at the 3 MB tested it took 25 s.
   - A 100 MB file is far beyond both: plain, as the plan says.
7. Open the syntax on a background thread at file open or first use: the first lines of a syntax pay about 40 ms
   (Rust) of lazy regex compilation.

## What was not measured

- Edits that add or remove a line (checkpoints after the edit need their indices shifted; the state work is the same).
- Highlighting on a background thread concurrent with typing, or any multi-threading; everything here is one thread.
- The viewer's actual theme/style pipeline beyond `HighlightIterator`; other themes; the `onig` engine (the viewer
  uses `regex-fancy`, so onig would be a different, probably faster, number).
- Other syntaxes of the 75 (only Rust, Markdown with embedded rust/json/python/bash/js, and long-line cases in JSON
  and JS); real-world files (the data is generated, so line-length mix and nesting are mine); TypeScript/TOML etc.
  are missing from the set anyway.
- Syntax set and theme memory in isolation; process memory is in `raw/` only as noisy private-bytes deltas.
- Whether ParseState equality alone is a sufficient convergence test (both parts were compared throughout).
- A quiet machine: no run had it. The Rust "(q)" runs were quieter, not quiet; the Markdown numbers carry larger error.
- Confirmation that fancy-regex hits its backtrack limit on the long unterminated string (inferred from timing and
  from reading syntect's source, not instrumented).
