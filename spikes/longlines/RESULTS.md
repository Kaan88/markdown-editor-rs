# Spike longlines: viewport-only shaping

Date 2026-11-12, Windows 11, release build (opt-level 3), parley =0.12.0, swash =0.2.10 (the
viewer's versions), Consolas 14 px (measured glyph advance 7.697 px, line height 18.2 px at
line-height 1.3). The shaper is the viewer's approach: one `FontContext::new()`, one reused
`LayoutContext<Brush>`, `ranged_builder` + `push_default` (family, size, line height, brush) +
`build` + `break_all_lines` + `align`.

**The machine was loaded the whole time** (other agents building spikes and the viewer). Timings
are the median of 7-9 runs, with min-max in brackets; each run averages several iterations for
small inputs. The same quantity differs up to 2x between runs made minutes apart (1 KB no-wrap:
0.11 ms in the "sizes" run, 0.22 ms in the "sweep" run), so treat every number as +-50% and prefer
the ratios. Code: `src/main.rs`; run `longlines sizes|sweep|strategies|raster|mem <bytes> <no|word|anywhere>`.

Test text: "minified JS-like" generated by an xorshift PRNG from 39 tokens (`function(`, `return `,
`e.length`, `"str"`, `=>` ...): ASCII only, spaces only after keywords (about one per 145 bytes),
so wrapping at 1200 px is mostly forced by UAX14 opportunities after `;` `,` `)` or spaces.
"Typical" lines are 80/120-column code-like text with spaces.

## Numbers

### Typical lines (no wrap)

| what | ms |
|---|---|
| shape one 80-col line | 0.012-0.017 (0.0105-0.0173) |
| same, with 10 colour spans (highlight-like) | 0.012 (0.0114-0.0118) |
| 60-line viewport x 80 col, a layout per line | 0.67 (0.66-0.78) |
| same with spans | 0.76 (0.75-0.78) |
| 60-line viewport x 120 col | 0.94 (0.94-0.95) |

A whole viewport re-shape is under 1 ms; one edited typical line is about 0.015 ms. Shaping a
typical line is not a concern for the 8 ms budget.

### One long line, whole-line shape (ms)

| size | no wrap | wrap 1200 px (UAX14) | wrap 1200 px (anywhere) |
|---|---|---|---|
| 1 KB | 0.112 (0.110-0.117) | 0.113 (0.111-0.114) | 0.114 (0.114-0.119) |
| 10 KB | 1.14 (1.13-1.20) | 1.14 (1.13-1.15) | 1.16 (1.15-1.33) |
| 100 KB | 11.2 (11.1-11.5) | 11.3 (11.2-11.4) | 11.4 (11.4-11.5) |
| 1 MB | 116 (115-117) | 119 (118-121) | 120 (118-131) |
| 10 MB | 2157 (2096-2351) | 2160 (1975-2706) | 2527 (2168-2653) |

(5 runs for 1 MB and up, 7 for the rest.) About 11 us per KB, i.e. 90 MB/s, linear up to 1 MB,
slightly worse above (10 MB is 18.6 us/KB). Wrapping adds almost nothing: line breaking is cheap
next to shaping. Wrap at 1200 px gave 8, 70, 690, 6904 and 69015 visual rows for 1 KB to 10 MB.

### Memory held by a Layout (fresh process per measurement, 5 runs each, results identical to 0.1 MB)

Private bytes (`PrivateUsage`) before shaping vs with the layout alive; "after drop" is what
stays allocated once the Layout is dropped (the `LayoutContext`'s retained scratch buffers).

| size | held with layout (no wrap / wrap) | still held after drop | peak working set (whole process) |
|---|---|---|---|
| 1 KB | 0.1 MB | 0.1 MB | 7.3 MB |
| 10 KB | 0.9 MB | 0.3 MB (0.8 in 3 of 10 runs) | 8.0 MB |
| 100 KB | 8.9 / 9.2 MB | 4.3-4.4 MB | 14.7-14.9 MB |
| 1 MB | 89.8 / 92.0 MB | 44 MB | 82.5-84.5 MB |
| 10 MB | 898 / 919 MB | 440 MB | 761-778 MB |

About 90-96 bytes of private memory per input byte while the layout is alive (wrapped about 2%
more), of which about 44 bytes per input byte is the context's scratch, which stays allocated
after the Layout is gone. A 10 MB line therefore holds about 440 MB for the rest of the process
unless the `LayoutContext` itself is dropped.

Crossings, taking both runs (the quieter "sizes" run and the loaded "sweep" run):

- **2 ms: about 12 KB (loaded) to 18 KB (quieter).**
- **8 ms: about 36-45 KB (loaded) to 70 KB (quieter).**

Dense highlight spans (one per 8 bytes, 12.5% more spans than a token highlighter would make)
cost 5-60% more, the gap growing with length. The hard-cap table below gives a third reading:
2.9 ms at 16 KB, 7.9 ms at 32 KB.

These are the cost of shaping alone. A keystroke also repaints (see rasterisation) and does
buffer, highlight and present work, so shaping needs to be well under 8 ms: a budget of 1 ms for
it means about 4 KB (0.8-1.1 ms in the sweep).

### Strategy A: shape only chunks on screen

Chunks of about N bytes, split at the first ASCII space/tab within 512 bytes after N, else at a
grapheme boundary (`unicode-segmentation` `GraphemeCursor`). The chunk covering the viewport
window is found by jumping to `pos / N * N` and moving to the next safe boundary (no scan of the
line). Cost per frame (or per edit), ms, median of 9, including finding the boundaries:

| line | chunk N | no wrap, view at start | no wrap, view at middle | wrap 1200 px, 60 rows (~9.3 KB) at middle |
|---|---|---|---|---|
| 1 MB | 256 | 0.028 | 0.043 | 1.75 (1.39-2.97) |
| 1 MB | 1024 | 0.105 | 0.108 | 1.72 (1.27-2.63) |
| 1 MB | 4096 | 0.48 (0.44-1.74) | 0.46 (0.44-0.92) | 1.79 (1.47-3.31) |
| 1 MB | 16384 | 2.3 (1.8-3.9) | 2.0 (1.8-4.7) | 6.0 (4.1-8.2) |
| 1 MB | 65536 | 11.7 (8.6-13.8) | 12.7 (11.0-15.8) | 13.3 (10.9-16.1) |
| 10 MB | 256 | 0.030 | 0.032 | 1.82 (1.41-4.84) |
| 10 MB | 1024 | 0.18 (0.11-2.06) | 0.18 (0.13-0.21) | 1.49 (1.29-3.74) |
| 10 MB | 4096 | 0.66 (0.48-1.62) | 0.59 (0.45-2.05) | 2.49 (1.52-4.51) |
| 10 MB | 16384 | 3.7 (2.8-5.5) | 3.5 (2.6-5.6) | 3.7 (2.9-5.4) |
| 10 MB | 65536 | 14.7 (13.0-17.5) | 14.2 (12.1-17.0) | 13.9 (12.6-16.5) |

The cost depends on the chunk size and the window, not on the line length: 1 MB and 10 MB give the
same figures. With N = 1 KB a no-wrap window costs 0.1-0.2 ms (the viewport is about 160 columns,
one or two chunks), an edit re-shapes one chunk (0.1 ms), and 60 wrapped rows cost about 1.5-1.8
ms. Chunks of 16 KB or more are not useful (they alone reach 2 ms).

Index cost: finding all chunk boundaries of a line by byte-offset jumps (N = 4096, no shaping)
was 0.004 ms for 1 MB and 0.05 ms for 10 MB. This is O(chunks), not O(bytes), because each jump
goes straight to `i + N` and only looks 512 bytes ahead. A real index would be updated per edit.

Memory: only the chunks on screen are held (a few KB of text, so about 100-400 KB of layout at
90 B/byte). The 900 MB of the 10 MB line never exists.

### Strategy B: hard cap, line shown truncated

Shape the first C bytes of the line only (cost is the whole-line shape of C bytes, no wrap):

| C | ms |
|---|---|
| 4 KB | 0.87 (0.66-1.08) |
| 8 KB | 1.41 (1.25-3.47) |
| 16 KB | 2.92 (2.44-5.17) |
| 32 KB | 7.88 (5.97-8.50) |
| 64 KB | 15.4 (11.3-22.2) |
| 128 KB | 28.0 (24.0-34.5) |

Cost is bounded and simple, but the rest of the line cannot be seen, selected or edited, and with
no wrap a screen shows about 160 columns anyway, so a cap in the thousands of bytes hides almost
everything a reader wants from a minified file.

### Rasterisation of a 60 x 120 viewport (7200 glyphs)

swash `Render` with `Format::CustomSubpixel([0.3, 0.0, -0.3])`, hinting off, 4 subpixel
positions, as in the viewer's `TextEngine`, then a plain blend into a 1000 x 1111 BGRA buffer
(the viewer's preblend LUT is not included, so a real blit is somewhat slower).

| | ms |
|---|---|
| cold: empty glyph cache, new `ScaleContext`, 156 unique (glyph, subpixel) rasters | 1.81 (1.66-2.71) |
| warm: all cached, lookup + blit of all 7200 glyphs | 1.73 (1.12-2.24) |

Cold minus warm is about 0.1 ms: rasterising 156 monospace glyphs costs next to nothing, and the
frame time is the lookup and blend of 7200 cached glyphs (about 0.24 us each). Note a full
viewport redraw is therefore about 1.7 ms before the viewer's LUT; an edit should repaint only
the edited line's band. Glyph cache holds 24.7 KB for this text (ASCII, one size); it grows with
distinct characters, sizes and the 4 subpixel positions (the cold test used proportional-free
Consolas, so 7.7 px advance spreads over all 4 positions).

## Conclusion and recommendation

1. Shaping cost is linear, about 11 us per KB (90 MB/s) on this loaded PC, and memory is about 90
   bytes per input byte (about 44 of them stay allocated in the `LayoutContext` after the layout
   is dropped). Whole-line shaping of a 1 MB line costs 120 ms and 90 MB; of a 10 MB line 2.2 s
   and 900 MB. Neither is acceptable in an editor that promises to open files without shaping
   what is not on screen.
2. A single-line re-shape crosses 2 ms at about 12-18 KB and 8 ms at about 36-70 KB. Typical
   lines (under 200 bytes) cost 0.02-0.05 ms.
3. **Strategy: chunked shaping of the visible window, with no hard cap.** Shape the whole line
   as one layout when it is at most 4 KB (under about 1 ms with spans). Above 4 KB, split it into
   chunks of about 1 KB (N between 1 KB and 4 KB; 1 KB gave 0.1 ms per no-wrap window and
   about 1.5 ms for 60 wrapped rows), at the next ASCII whitespace, else grapheme boundary, and
   shape only the chunks that touch the window plus one spare either side. An edit re-shapes
   the chunk it is in (0.1 ms) plus the next chunk if the split moved. Cost and memory then do
   not depend on line length.
4. A hard cap as a fallback only: if the editor decides a line is too long to be worth
   chunk-indexing (suggestion: over 10 MB, where a byte-offset index is still only 0.05 ms but
   horizontal positions and wrapped heights are guesses), show it plain and unwrapped. 8 KB cap
   shaped costs 1.4 ms, 16 KB costs 2.9 ms, so if a cap must exist for syntax highlighting
   (highlighter cost is not measured here) it should be tied to that, not to shaping.
5. Drop (or `LayoutContext::new()` over) the context after any layout over about 100 KB, or never
   shape that much at once; the retained scratch is 4 MB per 100 KB shaped.

## Not measured

- Wrapped-row heights across chunks. With wrap on, "which byte starts visual row k" needs either
  shaping all chunks before it once (about 11 us per KB, 1.2 s for 10 MB) or an estimate from the
  monospace advance (7.697 px per column here) that is corrected as chunks are shaped. I timed
  neither the estimator nor the correction; only the cost of shaping one window at an assumed
  position.
- Horizontal scroll mapping for no-wrap lines (x px to byte offset) needs a per-chunk width;
  exact for ASCII Consolas (advance times columns), not tested for non-ASCII, tabs, wide CJK
  or ligatures.
- Correctness at chunk seams: kerning/ligatures across the split, bidi, combining marks (the
  grapheme fallback is exercised nowhere because all test text is ASCII with spaces or the
  512-byte window found a space), selection and caret hit-testing across two layouts.
- Real syntax highlighting (syntect) cost; only synthetic colour spans were applied.
- Hinting, other sizes or DPI scales (the viewer's `scale`), other fonts, bold/italic runs.
- Rasterisation under load with the viewer's preblend LUT, and the `Layout`s' text drawing cost
  for the wrapped 60-row window.
- No quiet-machine run was possible; all timings were taken while other builds were running.
- Peak working set was read once at the end of each process, so it is the peak over that process
  (baseline about 7 MB with the font context), not per-phase.
- Memory for `FontContext` itself (system font enumeration) is in every baseline and not reported
  separately; the font's own data (Consolas, 453 KB) is shared.
