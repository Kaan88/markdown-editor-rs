# Spike "buffer": ropey against a piece table (and a String floor)

Run 2026-11-12 on the Windows 11 PC (28 logical cores). The machine was loaded: other agents were building
other spikes and the viewer at the same time, so every figure is noisy. Each cell below is the median of 5
runs, with the range in brackets. Every run is a fresh process (`buffer-spike run <impl> <file>`), so memory is
not polluted by an earlier run. `buffer-spike bench` spawns the runs and aggregates.

## What was compared

- **ropey**: `ropey` 1.6 (default features), `Rope::from_reader`.
- **piece**: my own piece table. Original buffer (the file bytes, never touched) + append-only add buffer +
  pieces `{buffer, start, len, lf}` held in a two-level structure (blocks of at most 128 pieces, each block
  caching its byte and line-break totals; lookups scan the blocks, then the pieces of one block). Line index: the
  offsets of every `\n` in the original buffer and in the add buffer (sorted `Vec<usize>`, binary searched
  inside a piece). Typing extends the last add-buffer piece in place instead of creating a piece. 128 was picked
  by trying 64/128/256 once each on the 100 MB file (one trial each, differences within what I would expect from
  noise). Not a balanced tree: this is the "Vec of pieces" variant with one extra level.
- **string**: floor. `String` + `Vec<usize>` of line starts (`insert_str`, `drain`, and a shift of every later
  line start).

All three buffers are driven by **byte offset** at the benchmark level (ropey needs `byte_to_char` first; that
conversion is inside its timings).

## Data

Generated by `buffer-spike gen` (deterministic xorshift, never committed, written to `target/data/`).
Mixed code-like lines (indented `let`/`fn`/`if`/`struct` lines), English comments, 3% Turkish comment lines,
3% CJK comment lines, 7% blank lines, 4% long lines (up to ~600 bytes), `println!` lines with Turkish text.
LF only.

| file | bytes | lines | bytes/line |
|---|---|---|---|
| 1mb | 1,048,595 | 18,449 | 56.8 |
| 100mb | 104,857,685 (100.0 MiB) | 1,852,171 | 56.6 |

The 100 MB file has 1.85 million lines, not the ~1.5 million in the brief (lines came out shorter than I
aimed for). That makes the line index somewhat heavier than the brief's file, not lighter.

## How it was measured

- Time: `Instant`. Memory: `K32GetProcessMemoryInfo` `PrivateUsage` (private bytes) minus the value just before
  the load (0.64 MiB), and `PeakWorkingSetSize` at the end. "MiB" throughout.
- Disk reads were warm (the OS had just written or read the file). **Cold-cache load was not measured.**
- Each run: load; first 60-line window; 100,000 line-to-byte lookups, 100,000 byte-to-line lookups, 10,000
  windows of 60 lines at random lines (all on the pristine buffer); 10,000 single-character inserts at random
  positions; 10,000 inserts at one advancing position (typing) starting in the middle of the file; 10,000
  single-character deletes at random positions; the same lookups again on the edited buffer (`_ed`); save the
  whole buffer to a new file (`BufWriter`, 1 MiB buffer, no fsync in the save timing; a `sync_all` afterwards
  measured about 0.06 ms, so durable-write cost is effectively not measured).
- Inserted characters cycle through ASCII, `ğ`, `ü` and `漢` (1, 2, 2, 3 bytes); deletes remove one whole
  character, and can remove a `\n`. The positions are chosen before the timer starts (snapped to char
  boundaries and adjusted for earlier edits with a Fenwick tree), so only the edit itself is timed.
- Correctness cross-check: in every run all three implementations return the same sums of line-to-byte lookups,
  byte-to-line lookups and window lengths (before and after the edits), the same final length and line count,
  and the same FNV hash of the saved file. The check lines at the end of each bench said "SAME in all impls and
  runs" (the three implementations were checked in separate bench invocations, but the hash and sums printed
  identical across them: 520789112053 for the 100 MB file).
- A "window" is a `&str` of 60 lines: borrowed when the lines sit in one chunk or piece, copied into a scratch
  `String` otherwise (the "needed a copy" rows count copies out of 10,000).

## Against the plan's budget (100 MB file)

- First frame under 500 ms: load is 74-88 ms in all three with a warm cache, plus under 10 us for the first
  window. That is the buffer part only: no shaping, no highlighting, no window creation. Passes with a large
  margin, which would survive a cold read from an SSD that I did not measure.
- Memory about file size plus 25%: after load, ropey 119.6 MiB (+19.6%), piece and string 117.3 MiB (+17.3%).
  The piece-table and string figure is the file bytes plus 14.1 MiB for the line index (8 bytes per line;
  4-byte offsets would halve it and cap files at 4 GiB). **After 30,000 edits ropey is at 130.9 MiB (+30.9%),
  over the budget, while the piece table is at 119.1 MiB (+19.1%).** The undo log is not in these numbers.

## Conclusion

**Recommendation: ropey.** Everything an editor does per keystroke or per frame costs microseconds in both ropey
and the piece table at 100 MB (0.9 us per random insert and 1.7 us per 60-line window for ropey), so speed on
these operations does not decide it. What decides it:

1. The piece table's lookups are only fast while there are few pieces. Line-to-byte went from 6.0 ms to 37.2 ms
   per 100,000 lookups (6x) after 30,000 edits, level with ropey, and my structure is linear in the number of
   blocks and pieces (about two pieces per random edit, no coalescing, no compaction), so it keeps getting
   slower the longer the file is edited (not measured beyond 30,000 edits). Keeping it flat means writing a
   balanced tree with cached counts, which is rewriting ropey. Ropey's cost is O(log n) whatever the edit
   history.
2. Ropey brings what the plan needs: a cheap `Rope::clone` (copy-on-write, documented, not exercised here) gives
   the highlighter thread and a save-while-typing path an immutable snapshot, and its line, char and byte
   conversions are already tested.
3. It meets the load budget (74 ms) and the memory budget after load (+19.6%).

The honest cost of ropey: it is the only one that goes over the memory budget after edits (+30.9% against
+19.1% for the piece table) in this run; its 60-line windows were always copied (a chunk is about 1 KiB) at about
1.7 us each; and line-to-byte and byte-to-line are 1.7-6x slower than the piece table's on an unedited file
(0.36 us against 0.06 us per line-to-byte lookup). None of that is near a frame budget. If memory after edits
matters more than I think, the piece table's measured advantage is real: 12 MiB at 100 MB.

The `string` floor is not an option beyond small files: 2.4-3.2 ms per edit at 100 MB (23.9 s for 10,000 random
inserts), against 7.7 us per edit at 1 MB. Its lookups are the fastest of all and its memory after load is the
file plus the index, but any edit costs a memmove of half the file plus a shift of the line index.

## API consequences

- **Indexing.** ropey edits by char index (`insert(char_idx, &str)`, `remove(char_range)`). The editor works in
  byte offsets (parley, syntect, regexes), so every edit pays a `byte_to_char` (included above) and every
  position given to the buffer must be on a char boundary. A piece table is bytes all the way (its slicing is
  unchecked UTF-8 by invariant: pieces are only cut at char boundaries). Either way the caret should be a byte
  offset in a grapheme-aware layer above the buffer.
- **Chunks.** ropey exposes `chunks()`, `chunk_at_byte`, `line(i)` and slices; text is not contiguous, so
  anything that wants a `&str` over several lines (shaping a window, a regex over the buffer, syntect line by
  line) goes line by line (`rope.line(i)` is a `RopeSlice`, usually one contiguous chunk, otherwise copy it) or
  collects into a scratch `String`; all 10,000 of my 60-line windows needed that copy. The piece table gives a
  contiguous `&str` only inside one piece (0% copies pristine, 47% after 30,000 edits). Never give the rest of
  the program a `&str` of the whole buffer.
- **Line breaks.** ropey 1.6 by default also treats lone `\r`, `\u{0B}`, `\u{0C}`, `\u{85}`, `\u{2028}` and
  `\u{2029}` as line breaks (cargo features `cr_lines` and `unicode_lines`). My benchmark data has none of them,
  so this was not exercised, and I did not test whether turning the features off gives LF-only lines. The plan
  wants CRLF files shown and saved as they were, so decide the line semantics first. The piece table and string
  count `\n` only, and `\r` is an ordinary trailing character.
- **Undo.** With ropey, store edits as `(byte_pos, removed: String, inserted: String)` as the plan says and apply
  the inverse through the same two calls; the removed text is the only copy of that text (ropey does not keep
  it). A piece table can store edits as pieces: a deletion is "these pieces were removed from here", nothing is
  copied, the add buffer is append-only, and undo splices the old pieces back. It would be the cheaper undo, at
  the cost of the add buffer never shrinking and the fragmentation above. Neither was implemented or measured.
- **Save.** ropey `write_to` walks the chunks, the piece table walks the pieces; both are `write_all` over
  slices, and both saved in 25-27 ms (100 MB, warm, no fsync) against 64 ms for the string.

## What was not measured

- Cold-disk load, `mmap` loading, or showing the first frame while the line index is still being built (a lazy
  index would remove part of the 75 ms; not tried).
- Anything beyond 30,000 edits: ropey's memory growth and the piece table's slowdown with more pieces were only
  observed at that one point, not as a curve.
- Multi-line pastes or deletes, a file made of one 100 MB line, CRLF files, files over 4 GiB, invalid UTF-8,
  other encodings.
- Memory of an undo log, and any concurrency (ropey's snapshot cloning was not exercised).
- ropey with `from_str` instead of `from_reader`, `ropey` 2.x, and ropey feature changes.
- The piece table is a spike, not a library: no coalescing of adjacent pieces, no block merging after deletes,
  linear scans, `usize` offsets everywhere, unchecked UTF-8. Its numbers after many edits are for this
  structure, not for a balanced-tree piece table.
- Allocator is the default Windows heap; another allocator would change the memory numbers.
- No UI was involved; nothing here says anything about how the editor looks or feels.

## Reproduce

```
cd spikes/buffer
CARGO_TARGET_DIR=$PWD/target cargo build --release
target/release/buffer-spike.exe gen 1 target/data/1mb.txt
target/release/buffer-spike.exe gen 100 target/data/100mb.txt
target/release/buffer-spike.exe bench 5 ropey,piece target/data/100mb.txt
target/release/buffer-spike.exe bench 5 string target/data/100mb.txt   # about 12 minutes
```
