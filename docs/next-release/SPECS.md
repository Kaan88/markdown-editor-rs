# Next-release work: rules and feature specs

Written for agents on the Linux machine on 2026-11-14. Paths such as `~/src/md/wt/<repo>-<key>` were that machine's git worktrees: on a fresh clone use the branch `f/<key>` instead, and any shared build folder you like. See "START HERE" in `docs/HANDOFF.md` for the state of each branch.

## Rules for every feature

You work on two sister Rust desktop apps (winit 0.30 + softbuffer, every control hand-drawn by a shared Painter; no GUI toolkit): mdedit, a light text editor (GitHub Kaan88/markdown-editor-rs) and mdview, a Markdown viewer (Kaan88/markdown-viewer-rs). Both build on shared crates (Kaan88/markdown-shared-rs) pinned by git rev in the Cargo.toml files (all mdshared-* lines, in every Cargo.toml of the app that names them).

Where you work: one git worktree per feature, ~/src/md/wt/edit-<key> (mdedit) or ~/src/md/wt/view-<key> (mdview), on branch f/<key>, already created. A few other agents work on other features in sibling folders: NEVER touch a folder that is not for a feature in your own queue.
If you must change the shared crates: create your own shared worktree with  git -C ~/src/md/shared worktree add ~/src/md/wt/shared-<your feature key> -b f/<your feature key> origin/main  (retry after a few seconds if git reports a lock), commit there, git push origin f/<your feature key> (never push shared main, never force-push), and pin that commit rev in your app worktree; refresh Cargo.lock (cargo update -p mdshared-ui -p mdshared-app -p mdshared-text -p mdshared-highlight -p mdshared-fetch as applicable; it only resolves). Keep every third-party crate in Cargo.lock at the version it had: if the lock update moved unrelated crates, restore those entries.

Read first, in your worktree: docs/HANDOFF.md (top, and the newest release section), docs/PLAN.md (budgets), docs/DESIGN.md as needed. Then read the code you will change before designing anything.

Hard rules:
1. Verify locally first, then on CI. Local builds are allowed and expected, with ONE shared build folder per repository so twenty worktrees do not fill the disk: always set CARGO_TARGET_DIR=$HOME/.cache/md-build/edit for mdedit, $HOME/.cache/md-build/view for mdview, $HOME/.cache/md-build/shared for the shared repo (export it at the start of every shell command that runs cargo; never build into a worktree's own target folder, and delete one if you created it by mistake). Other agents use the same folders, so a cargo command may wait for the build lock ("Blocking waiting for file lock"): that is normal, wait, give long timeouts (10 minutes, or run in the background), never kill another agent's cargo. Use debug builds: cargo check, cargo clippy --workspace --all-targets -- -D warnings, cargo test (prefer -p <crate> and a test-name filter while iterating, the whole workspace once before pushing), cargo fmt. Do not make release builds locally and do not open real windows on this machine (it is the owner's desktop); headless --shot rendering of a debug build is fine if you want a quick look (cargo run -p <bin> -- --shot ..., see tests/shots.sh for the arguments). When it passes locally: git push -u origin <branch>, then in the worktree  gh workflow run ci.yml --ref <branch> ; find the run with  gh run list --workflow ci.yml --branch <branch> --limit 1 ; then WAIT WITHOUT POLLING: the GitHub API quota of this account was exhausted once by agents polling. Never use gh run watch. Sleep 12 minutes (sleep in the background or in chunks), then one  gh run view <id> --json status,conclusion ; if not finished, sleep 5 more minutes between single checks. Start CI once per feature, after everything passes locally. If gh answers "API rate limit exceeded", sleep 15 minutes and carry on with local work meanwhile. CI runs fmt, clippy -D warnings, all tests and the screenshot script on Linux and on Windows (which nothing here can check locally) and uploads the shots as artifacts shots-linux / shots-windows (gh run download <id> -n shots-linux -D ~/src/md/shots-review/<branch with / replaced by ->/linux). When CI fails read the log (gh run view <id> --log-failed), fix, push, run again. You are not done until CI is green on both systems.
2. These apps are valued for being fast to open and light. A feature must add no work at startup and nothing on the keystroke or scroll path when it is not in use: load lazily, no new threads at launch, no new heavy dependencies (no new crate without a strong reason; say so if you add one). Budgets (docs/PLAN.md) are measured on release builds, which you do not make: say that they were not measured, and explain why your change cannot move them.
3. Quality over quantity. The owner said: "app is really good, let's not ruin it." Follow the existing interface exactly: spacing, fonts, Palette colours, icons from the shared glyph set (add a glyph in the existing style only if needed), wording in the style of the existing strings, keyboard access for everything, entries in menus, the command palette and Keyboard shortcuts where commands exist, a setting only when really needed. Do not change unrelated behaviour. No half-working parts: what cannot be done well is left out and reported.
4. Merge-friendliness: other features edit the same central tables (menus, commands, key tables, strings, settings rows, tests/shots.sh). Make additive, minimal edits there; do not reorder, rename or reformat existing code; put new logic in new modules/files where sensible.
5. Shortcuts already assigned to features (do not use them for anything else, and use yours): word completion Ctrl+Space; column selection Alt+Shift+arrows and Alt+drag; find in folder (viewer) Ctrl+Shift+F; presentation (viewer) F5; history (viewer) Alt+Left / Alt+Right. Any other new shortcut: check the existing key tables, prefer none over a doubtful one.
6. Code both apps could use goes into the shared crates, not copied twice.
7. Tests: unit tests for all logic, app-level tests in the style of the existing ones, and a --shot screenshot of every new visible state added to tests/shots.sh in the existing way. Download the shots from the green run and LOOK at each new one (Read the PNG), in both themes where applicable; fix what looks wrong. Never weaken, skip or ignore an existing test.
8. Works on Windows and Linux (Wayland and X11); platform code behind cfg with a sensible fallback.
9. Docs: do NOT edit README.md, docs/PLAN.md, docs/HANDOFF.md, docs/DESIGN.md or release notes (twenty branches would conflict). Instead write docs/next/<feature key>.md in your app worktree with these sections: "README" (the text to add to the feature list and shortcut table), "DESIGN" (the behaviour as specified, rules and edge cases), "Release note" (one or two lines), "Handoff" (what was built, decisions you took, what was NOT verified, what was left out). A later agent folds these into the real docs.
10. Before starting: git status in your worktree. If a previous agent left work there (commits on the branch or uncommitted changes), read it and continue from it rather than starting over. Commit in small coherent commits; messages end with the line: Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>
11. Never merge into main or next, tag, release or bump versions. Never use pkill -f. Never touch the owner's real settings files or installed apps. Do not run the apps.
In the result, base = the commit your branch started from (git merge-base with origin/main unless told otherwise), head = your branch's final commit.


# Rounded corners

## rounded-corners — Rounded window corners (both apps, shared code)

Both apps draw their own title row and, on Wayland, their own client-side shadow margin (shared feature client-margin, forked winit/softbuffer, see ~/src/md/shared-next-edit/docs/LINUX.md and the "rounded corners" notes in each app's docs/PLAN.md "Next release"). Implement what those notes describe: the window's outer corners rounded with a default radius of 8 logical px scaled with the display; square when maximised, tiled or fullscreen; a setting "Window corners" in each app's Settings with a small set of choices that includes 0 (square) and follows the settings style already there. Per platform: Windows 11 = ask DWM for rounded corners (DWMWA_WINDOW_CORNER_PREFERENCE) rather than drawing, Windows 10 = square, no error; Wayland with the client-drawn margin = draw the rounded shape with transparent corners in the ARGB buffer and round the shadow to match; KDE with the KWin shadow protocol and X11 = only where a correct result is possible (transparent corners need an ARGB surface; if it is not, leave the window square there and say so). The shape must be anti-aliased, must not cost a full-frame pass per frame (mask only the four corner squares, only when they were repainted), and partial repaints must stay correct. Use one lane for shared: ~/src/md/shared-next-edit. Do the editor first, then the viewer with the same shared code. Add shots at scale 1 and 2 in both themes that show a corner clearly (if --shot renders only the content without window shape, add a unit test of the corner mask instead and say so).

# Editor features

## autosave-recovery — Autosave and crash recovery (mdedit)

Unsaved text must survive a crash, a kill or a power loss. Design: a recovery store in the app's data folder (next to the session; honour MDEDIT_SETTINGS for tests), one file per modified document holding its text and the path, encoding, line ending and a hash/mtime of the file it came from (untitled documents too). Written on a background thread after a pause in typing (a few seconds idle, and at most every ~30 s while typing), atomically (write temp, rename); removed on save, on close-without-saving, and on a normal exit where the session already keeps unsaved documents (read how the session handles unsaved documents today and do not duplicate or fight it: if the session already restores unsaved text on a normal exit, the recovery store only has to cover abnormal exits and must reuse the same format/code where sensible). At the next start, if recovery files exist from a run that did not exit normally, restore those documents as modified tabs and say so in one unobtrusive bar/toast in the existing style ("Recovered N unsaved documents"), never silently overwrite a file on disk, and if the file on disk changed since, keep both (the recovered text as modified, with the existing changed-on-disk handling). Large documents: do not block typing, do not write a 500 MB document every 30 s (set a size limit in limits.rs and say what happens above it). Not "autosave to the real file" unless the app already has such a setting; if you add that as an option keep it off by default. Startup cost: one directory listing, only reading files when some exist.

## column-selection — Column (block) selection (mdedit)

Alt+drag (and Alt+Shift+arrow keys; check for clashes with existing shortcuts and with window-manager Alt+drag on Linux, and offer Ctrl+Alt or Shift+Alt as needed, consistent across platforms as far as possible) selects a rectangle: implement it on top of the existing multi-caret/multi-selection model as one selection per line, in visual columns (tabs and wide characters counted by display width; lines shorter than the column get a caret at their end, no virtual space unless the editor already has it). Typing, delete, paste (a clipboard with as many lines as carets pastes one line per caret, as the existing multi-caret paste does or should), copy (lines joined with the document's line ending) and undo as one step must all work. With word wrap on, define the behaviour in logical lines and say so. Read how carets, selections, drag and wrap work before designing.

## multicaret-line-commands — Multi-caret support in the line commands (mdedit; agreed item)

The line commands (sort lines, remove duplicate lines, join lines, heading and list/Markdown formatting commands, table alignment, move/duplicate/delete line, comment, case conversion, trim) currently act on the main caret or selection only, or behave inconsistently with several carets. Audit every one: with several carets/selections each command must act on the union of the touched lines or per selection, whichever is the natural meaning (document the rule per command in DESIGN.md), keep carets in sensible places, and undo in one step. Add tests per command with two and three carets, overlapping and adjacent selections.

## word-completion — Word completion and snippets (mdedit)

Light completion without a language server. (1) Word completion: on a shortcut (Ctrl+Space; check clashes, e.g. input-method switching on Linux, and offer an alternative) and, only if a setting is on (default off), automatically after typing 3+ word characters, show a small popup list at the caret (existing popup/menu drawing, up to ~8 rows, fuzzy or prefix match, using the shared fuzzy matcher if it fits) of words from the current document and other open documents; Up/Down/Enter/Tab accept, Escape closes, typing narrows, it never steals plain Enter when not open. Word index built lazily on first use and updated incrementally or rebuilt off the keystroke path with a cap for huge files (limits.rs). Works with multiple carets (completes at each) or is disabled then: decide and document. (2) Snippets: a small user file (snippets.toml or similar beside the settings; none shipped by default except a few for Markdown such as a table, a code fence, a link) mapping a trigger word and optional file type to text with tab stops $1 $2 $0; they appear in the same popup, Tab moves between stops. If tab stops make it too large to do well, ship snippets with a single caret position ($0) and say so. A command "Open snippets file". No cost when unused.

## table-editing — Markdown table editing help (mdedit)

In a Markdown file, with the caret inside a pipe table: Tab / Shift+Tab move to the next/previous cell (Tab in the last cell adds a row), Enter at the end of a row adds a row with empty cells, and the table's columns are re-aligned (padding cells to the column width by display width, respecting the alignment row :--- :---: ---:) when the caret leaves a cell via Tab or by an explicit command "Align table" (one may exist already: reuse and extend it), never on every keystroke. Commands: insert/delete row, insert/delete column, move column left/right, in the Markdown submenu and the palette. One undo step each. Must not hijack Tab outside tables or when a selection spans lines (indent stays). Handle escaped pipes \| and pipes inside inline code, wide characters, tables inside block quotes or lists (indent prefix kept), and ragged rows. A setting to turn the Tab behaviour off if the Settings already groups Markdown helpers.

## paste-image — Paste an image into a Markdown file (mdedit)

Paste (Ctrl+V) in a saved Markdown document when the clipboard holds an image and no text: save it as PNG beside the document (default folder: same folder; a setting for a subfolder name such as "images" if Settings has a Markdown group) with a name from the document name plus a counter or timestamp that does not collide, and insert ![](relative/path) at the caret with forward slashes and spaces percent-encoded; one undo step removes the text (the file stays; say so in the toast: "Image saved as ..."). Unsaved/untitled document: explain in a toast that the file must be saved first, do nothing else. Also when files are dropped on or pasted (file list on the clipboard) into a Markdown document as image files: insert a relative link instead of opening the image, only if that is consistent with how file drops work today; if drops open files today, leave drops alone and do paste only. Read how the clipboard is accessed today (which crate, per platform; Wayland and X11 and Windows) before deciding: getting image data must not add a heavy dependency; PNG encoding likewise (check what is already in the dependency tree). If the clipboard layer cannot deliver images on a platform without a large addition, implement where it can be done well and report the rest as left out.

## compare-copy-across — Copy a change across in compare (mdedit; agreed item)

The compare view (two files side by side, compare with saved, compare panes) shows differences. Add: with the caret in a changed block, commands "Copy this change to the other side" and "Take this change from the other side" (wording in the app's style), also as small arrow buttons in the gutter between/at the changed blocks if the compare view has a place for them that fits its look, and next/previous change if missing. The target must be an editable document (comparing with saved: only the working side changes); undo in one step on the changed document; the diff refreshes afterwards. Read the compare code first and keep its performance on large files.

# Viewer features

## folder-search — Search across the open folder (mdview; agreed item)

With a folder open in the files pane, a "Find in folder" command (shortcut Ctrl+Shift+F unless taken) opens a results panel or dialog in the existing style: a query box with the same options as find-in-page, results grouped by file with the matching line and the match highlighted, searched on a background thread over the Markdown/text files the pane shows (same ignore rules and size limits), streaming results in, cancellable, capped with a clear "more results not shown" line. Enter or click opens the file at the match (scrolls the rendered page to it and highlights it as find-in-page does). mdedit has "find in files": look at ~/src/md/edit-next for its searcher and results UI, and move what both can use into the shared crates rather than writing a second one (the editor is being changed by another lane at the same time: do not edit the editor's worktree; if moving code to shared would require editor changes, add the shared code in a way the editor can adopt later and note it).

## code-copy-button — Copy button on code blocks (mdview; agreed item)

When the pointer is over a rendered code block, a small copy button (shared glyph, existing hover/tooltip style) appears at its top-right corner; a click copies the block's source text exactly (no line numbers, trailing newline handled consistently) and the button shows a check mark briefly. Keyboard: a command "Copy code block" for the block at the focus/selection or the first visible one, in the palette. It must not shift layout, must not cover the first line's text in narrow blocks more than necessary, must scroll with the page, and must not add per-frame cost when the pointer is elsewhere. Also for Mermaid/math source blocks only if natural.

## copy-rich-text — Copy as rich text (mdview; agreed item)

First find out what a copy of a page selection puts on the clipboard today. Goal: copying a selection puts both plain text and HTML (text/html; on Windows the CF_HTML format with its header offsets) so a paste into a word processor or mail keeps headings, emphasis, links, lists, tables and code. Plain text stays as it is. Add "Copy as Markdown" (the source of the selected blocks) if the selection can be mapped back to source ranges; otherwise leave it out. Check how the clipboard is written per platform (Windows, Wayland, X11) and whether multiple formats are possible with the current layer without a heavy dependency; implement where it can be done properly and report the rest. HTML produced from the document model already parsed, with no external resources and escaped correctly; unit-test the HTML and the CF_HTML header arithmetic.

## export-print — Export to HTML and print (mdview; agreed item)

First check what exists. Add "Export as HTML..." : a single self-contained .html file of the current document with embedded CSS matching the page look (light theme by default, respecting the chosen page font and width), local images embedded as data URIs up to a size cap or linked relatively (decide, document), code highlighting colours, tables, task boxes, math and diagrams as they can be represented (if the engine renders them to images/SVG reuse that; otherwise keep the source in a pre block and say so). Reuse the HTML writer of the copy-as-rich-text feature if it exists on branch next (shared function). "Print..." : the simple, robust route is exporting to a temporary HTML file and opening it in the default browser with a print stylesheet (and say in the UI that the browser prints it, e.g. "Print (opens in browser)"); do not attempt native printing or PDF generation unless it is clearly small. Save dialog asynchronous as the other dialogs are.

## toc-follow — Table of contents follows the scroll position (mdview)

First check what the outline pane does today. Goal: the outline highlights the heading of the section at the top of the viewport as the page scrolls, and keeps that row visible in the outline (scrolling the outline minimally, not while the pointer is over the outline or the user scrolls it). Computed from the already-known heading positions with a binary search on scroll change, no layout work. Clicking a heading still jumps; the highlight then matches. If this exists already, verify it with tests and fix gaps instead.

## history — Back and forward history (mdview)

Following a link to another local document or to an anchor in the same document, opening from the outline of another file, or jumping from search results records a history entry (document, scroll position, anchor) per tab. Back / Forward: Alt+Left / Alt+Right, mouse buttons 4/5, toolbar buttons only if the bar has a natural place consistent with its design (otherwise menu and palette only), restoring the exact scroll position. History is per tab, capped, not persisted across restarts unless the session already stores per-tab state where it fits trivially. Check existing behaviour first (there may be partial support) and how links open (same tab or new tab).

## hover-previews — Footnote and link previews on hover (mdview)

Resting the pointer on a footnote reference shows the footnote's text in a small card near the pointer, rendered with the page's text styles (a few lines, capped width and height, ellipsis). Resting on an internal link to a heading (same document) shows that heading and the first lines under it; a link to another local Markdown file shows its title and first lines, read lazily on a background thread with a small cache, never for remote URLs (those keep the existing URL hint). Uses the existing tooltip/overlay timing and style, disappears on move/scroll/key, no cost when the pointer is not on a link, and a setting to turn previews off if Settings has a fitting group. If the renderer does not support footnotes at all, say so and do the link previews only.

## watch-folder — Watch the open folder (mdview)

The viewer already reloads an open document when it changes on disk (check how: polling or OS notifications). Extend to the open folder: the files pane picks up created, deleted and renamed files and folders without a manual refresh, and open tabs of changed files reload as they do now. Use the mechanism already in the app; if it polls, poll the expanded folders' mtimes at a low rate only while the window is visible and the pane is shown (idle CPU budget!), and stop when hidden/minimised. No new dependency unless the app already has a watcher crate. Keep expansion state, selection and scroll of the pane across refreshes. Debounce bursts (git checkout).

## presentation — Presentation mode (mdview)

A command "Present" (F5 unless taken; also in the menu and palette) shows the current document as slides in fullscreen: slides split at horizontal rules (---) when the document has any, otherwise at level 1 and 2 headings. Each slide is rendered by the normal page renderer with a larger zoom chosen to fit comfortably, centred, with the page's theme; Right/Space/PageDown/click next, Left/PageUp previous, Home/End, a small slide counter that fades, Escape leaves and returns to the same place in the document. A slide taller than the screen scrolls with the wheel/arrows before advancing. Front matter is skipped. Live reload keeps the current slide index. Reuse focus mode/fullscreen code. No cost outside presentation mode. Add shots of a slide in both themes.

# Cross-app features

## live-preview-unsaved — Live preview for a never-saved document (both apps; agreed item)

mdedit can show a Markdown document in mdview side by side with live preview of unsaved text (shared sister protocol: ~/src/md/shared-next-edit/docs/SISTER.md, crate mdshared-app sister module; Request has path, text, live_off...). Both lanes are finished now: you may change both app worktrees (~/src/md/edit-next and ~/src/md/view-next) and the shared worktree ~/src/md/shared-next-edit; CI must be green in BOTH apps.

## finer-sync — Finer scroll sync inside long blocks (both apps; agreed item)

With the side-by-side preview, the viewer follows the editor's caret/scroll by source line (see SISTER.md and the "follow" handling in both apps). Inside a long paragraph, list or code block the sync is coarse (block start). Make it finer: map a source line (and for wrapped paragraphs the offset within the paragraph) to a y inside the rendered block: exactly for code blocks (line n of the block), by source-line-to-rendered-line interpolation for paragraphs and list items, by row for tables, and vice versa if the viewer reports its position back to the editor. Smooth, no jitter when typing at the end of a document, no extra layout passes (use positions the renderer already has, or record per-line offsets while laying out, at negligible cost). You may change both app worktrees and ~/src/md/shared-next-edit; CI green in BOTH apps; unit tests for the mapping.
