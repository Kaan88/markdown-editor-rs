# The menu fade (`f/motion`) against `main`

Measured 2026-11-25 on the Windows PC with `tools/compare-builds.py` on `fixtures/sample.rs`, runs
interleaved, every window `--behind` (`MDEDIT_ARGS=--behind`), `--no-session`, `MDEDIT_SETTINGS`
naming a scratch `settings.ini` (one file for all the runs). Release builds of the one worktree,
copied aside as they were made:

- **main**: `02bb2a3`, shared at `ac9fde1`.
- **pin**: `8e2a919`, the shared crates moved to shared `main` `48eb3ce`, nothing else.
- **after**: the branch with the fade (117 ms), the Animations setting, the settled watch and the
  tests (`1c4c259`, main `929b116` merged in).

**Verdict.** No budget moved beyond this PC's noise, which an A/A run puts at about a millisecond
on the first frame's median and a range of 30 ms either way. Keystroke and scroll did not move (a
frame with no menu asks the animator for nothing, and `begin_frame` and `end_frame` on an empty
animator are a few comparisons). Idle memory is the same before a menu opens and 0.3 MiB more
after one (27.3 MiB). The fade adds seven frames of the menu's bounds and no CPU that Windows'
15.6 ms process times can see. Nothing new runs on the launch path except constructing an empty
`Animator` (two empty `HashMap`s, no allocation) and reading `prefs.animations`; the system's
motion setting is read, and its watch started on a helper thread, once the window has settled.

## Idle memory after the first menu

`--run OpenRecent` (the Recent menu opens half a second after the first frame and stays open),
private bytes read 4 s after launch, once the fade is over; 7 interleaved runs each.

| | main | after |
|---|---|---|
| Idle private, before the menu (the trace) | 27.0 MiB | 27.0 MiB |
| Private with the menu open, median | 27.0 MiB (26.5 to 27.4) | 27.3 MiB (27.0 to 27.6) |

The 0.3 MiB is not traced to its cause; likely the watch's thread and hidden window, and the backing (let go when the
menu arrives, kept by the allocator); within the 30 MiB budget.

## The fade itself, and idle CPU

Each build started with `--trace --size 1280x800 --run OpenRecent --exit-after-ms 32000` and left
alone, behind the others.

| | main | after |
|---|---|---|
| Frames in 32 s | 62 | 69 |
| The menu opening | 1 frame, 690 rows | 1 frame, 690 rows, 1.4 ms, then 7 frames of 161 rows, 0.36 to 1.19 ms each |
| Other frames | 60 of 734 rows: the caret's blink | the same 60 |

The seven extra frames are the fade (117 ms at 60 frames a second, and the frame that sees it
arrive), each drawing and presenting only the menu's bounds (161 device rows of 800). After them
the window draws nothing but the caret's blink, as `main` does: no timer is left.

CPU is Windows' process time, in ticks of 15.6 ms. Over 32 s, CPU to exit read 203 to 266 ms for
main, 188 to 297 for the pin and 250 to 359 for after, in runs taken while the runs above were
being taken. To see whether that was the fade or the watch, `after` alone was run 20 s at a time,
interleaved, four rounds (a fifth overlapped another run and is left out), CPU from settled to
exit:

| `after`, 20 s | from settled to exit |
|---|---|
| Recent opened, fading | 47, 109, 47, 78 ms |
| Recent opened, Animations off (no fade, no watch) | 63, 63, 47, 78 ms |
| No menu (the watch only) | 47, 16, 16, 47 ms |

The fade and the watch cost nothing these figures can show; the 32 s spread is the PC's.

Closing a menu was not driven in a window (there is no flag for it); `motion_tests` checks that a
closed menu leaves no deadline and no frame.

The pin's `Cargo.lock` change is two things (D-234): a new `libloading 0.9.1` for `mdshared-fetch`
(off Windows; `0.8.9` kept), and `mdshared-text` now depending on `zune-jpeg`, already in the lock.

## Not measured

The 100 MB file (nothing of the fade is on its load path); a frosted window (the frost-safe fade
was not seen on one); a menu over a dialog; Linux and macOS; the system's "Animation effects"
switched while the window runs (the wake is tested headless only).
