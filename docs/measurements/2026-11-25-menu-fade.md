# The menu fade (`f/motion`) against `main`

Measured 2026-11-25 on the Windows PC with `tools/compare-builds.py` on `fixtures/sample.rs`, runs
interleaved, every window `--behind` (`MDEDIT_ARGS=--behind`), `--no-session`, `MDEDIT_SETTINGS`
naming a scratch `settings.ini` (one file for all the runs). Three release builds of the one
worktree, copied aside as they were made:

- **main**: `02bb2a3`, shared at `ac9fde1`.
- **pin**: `8e2a919`, the shared crates moved to shared `main` `48eb3ce`, nothing else.
- **after**: the branch with the fade, the Animations setting and its tests (`e2691ec`).

**Verdict.** No budget moved beyond this PC's noise. Keystroke and scroll did not move (the fade
adds nothing to either path: a frame with no menu asks the animator for nothing, and `begin_frame`
and `end_frame` on an empty animator are a few comparisons). Idle memory is the same. The first
frame read +9.9 and +5.8 ms in two runs of main against after, and -1.3 and -3.1 ms in the runs of
pin against after and main against pin: the ranges overlap throughout, and the day's spread is
85 to 122 ms for the same exe. Nothing new runs on the launch path except constructing an empty
`Animator` (two empty `HashMap`s, no allocation) and reading `prefs.animations`; the system's
motion setting is read, and its watch started (a thread and a hidden window, on a helper thread),
only when the first menu that could fade opens.

## The fade itself, and idle CPU

Each build started once with `--trace --size 1280x800 --run OpenRecent --exit-after-ms 32000`
(the Recent menu opens half a second after the first frame and stays open; the window is left
alone for 32 s, behind the others).

| | main | after |
|---|---|---|
| Frames in 32 s | 62 | 72 |
| The menu opening | 1 frame, 690 rows, 2.2 ms | 1 frame, 690 rows, 3.2 ms, then 10 frames of 161 rows, 0.46 to 1.37 ms each |
| Other frames | 60 of 734 rows: the caret's blink | the same 60 |
| CPU from idle to exit | 234 ms | 219 ms |

The ten extra frames are the fade (167 ms at 60 frames a second, and the frame that sees it
arrive), each drawing and presenting only the menu's bounds (161 device rows of 800). After them
the window draws nothing but the caret's blink, as `main` does: no timer is left. The CPU figures
are Windows' process times at its 15.6 ms granularity, and are equal within it.

Closing a menu was not driven in a window (there is no flag for it); `motion_tests` checks that a
closed menu leaves no deadline and no frame.

The pin's `Cargo.lock` change is two things (D-233): a new `libloading 0.9.1` for `mdshared-fetch`
(off Windows; `0.8.9` kept), and `mdshared-text` now depending on `zune-jpeg`, already in the lock.

## Not measured

The 100 MB file (nothing of the fade is on its load path); a frosted window (the frost-safe fade
was not seen on one); a menu over a dialog; Linux and macOS; the system's "Animation effects"
switched while the window runs (the wake is tested headless only).
